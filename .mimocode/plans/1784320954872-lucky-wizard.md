# TurboPay Codebase Audit — Complete Plan

## Executive Summary

TurboPay is a fintech payment SDK + Next.js web app with 80+ Prisma models, 7 provider adapters, and a complex migration history. The codebase has **two critical systemic issues** that must be fixed before anything else works:

1. **Prisma schema drift** — 80+ models in schema.prisma, but only 66 tables in the initial migration. Missing columns, unique constraints, indexes, and relations cause CI/CD failures.
2. **SDK vs App code duplication** — `src/` (SDK) and `turbopay-complete-latest/` (app) have parallel implementations that drift apart.

---

## Phase 1: Fix CI/CD (CRITICAL — blocks all other work)

### Problem
The migration history is fundamentally broken:
- Initial migration `20260629000000` creates 66 tables
- Subsequent migrations (`20260705`, `20260711`, `20260715`, `20260716`) try to ALTER tables and CREATE INDEX on tables that don't exist yet
- Schema has 80+ models but many are missing from any migration
- Unique constraints (`@unique`) in schema are not in the database
- `ON CONFLICT` upserts fail because unique indexes don't exist
- `phone NOT NULL` constraint in initial migration conflicts with nullable schema

### Solution: Squashed Migration
Replace ALL existing migrations with a single squashed migration that creates the database as it exists today.

**Steps:**
1. Generate a fresh migration from the current schema using `prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script`
2. Replace `prisma/migrations/` with a single `20260000000000_initial/` migration containing the full SQL
3. Update `migration_lock.toml`
4. Update CI workflow to use `prisma migrate deploy` (already done)
5. Verify the migration applies cleanly in CI

**Files to modify:**
- `turbopay-complete-latest/prisma/migrations/` — replace all migration dirs
- `.github/workflows/ci.yml` — already uses `prisma migrate deploy`

**Estimated effort:** 1-2 hours
**Risk:** Medium — this is a clean-slate approach, safer than patching individual migrations

## Phase 2: Detailed Implementation Plan

### Root Cause Analysis

The schema has **80+ models** with hundreds of fields, unique constraints, and indexes. The migration history has 5 files:

| Migration | Creates | Modifies |
|-----------|---------|----------|
| `20260629000000_initial_postgres_schema` | 66 tables | — |
| `20260705000000_add_missing_columns_and_indexes` | — | ALTERs User/Session/Transaction + indexes (references AsyncTask which doesn't exist yet) |
| `20260711120000_make_email_optional` | — | ALTERs User.email DROP NOT NULL |
| `20260715000000_add_apple_id_and_missing_columns` | — | ALTERs User for appleId |
| `20260716000000_add_missing_tables_from_schema` | 27 tables + ALTERs for missing columns | Still incomplete |

**CI error chain:**
1. `migrate deploy` runs migrations in order
2. Migration 20260705 tries `CREATE INDEX ON "AsyncTask"` — table doesn't exist → FAIL
3. Even after patching that, tests fail with missing columns (`User.country`, `User.gender`, `ProviderConfig.costBasisPoints`)
4. Even after adding those, tests fail with missing unique constraints (`ON CONFLICT` errors)
5. Each fix reveals more missing pieces

### Approach: Replace All Migrations

**Why this is safe:**
- CI creates a **fresh PostgreSQL database** each run — no data to preserve
- The `migrate_lock.toml` (provider = "postgresql") stays the same
- `prisma migrate deploy` just applies pending migrations — a single fresh migration applies cleanly

**Why NOT incremental fixes:**
- Each fix reveals 2-3 more missing pieces (columns, constraints, indexes)
- The initial migration itself has issues (phone NOT NULL vs schema nullable)
- Trying to fix 5 broken migrations is harder than replacing them with 1 correct one

### Step-by-Step Implementation

#### Step 1: Generate the squashed migration SQL
```bash
cd turbopay-complete-latest
npx prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script > /tmp/squashed.sql
```
This produces the COMPLETE SQL to create the schema from scratch.

#### Step 2: Delete all existing migrations
```bash
rm -rf prisma/migrations/20260629000000_initial_postgres_schema
rm -rf prisma/migrations/20260705000000_add_missing_columns_and_indexes
rm -rf prisma/migrations/20260711120000_make_email_optional
rm -rf prisma/migrations/20260715000000_add_apple_id_and_missing_columns
rm -rf prisma/migrations/20260716000000_add_missing_tables_from_schema
```

#### Step 3: Create new squashed migration
```bash
mkdir -p prisma/migrations/20260718000000_initial
cp /tmp/squashed.sql prisma/migrations/20260718000000_initial/migration.sql
```

#### Step 4: Verify migration_lock.toml is correct
Should contain:
```toml
# Please do not edit this file manually
# It should be added in your version-control system (i.e. Git)
provider = "postgresql"
```
This stays unchanged.

#### Step 5: Verify the migration applies cleanly locally
```bash
# Start a temp PostgreSQL (Docker)
docker run -d --name tmp-pg -e POSTGRES_USER=test -e POSTGRES_PASSWORD=test -e POSTGRES_DB=test -p 5432:5432 postgres:16-alpine

# Apply migration
DATABASE_URL="postgresql://test:test@localhost:5432/test" npx prisma migrate deploy

# Check for errors
```

#### Step 6: Commit and push
```bash
git add turbopay-complete-latest/prisma/migrations/
git commit -m "fix: replace broken migration history with squashed migration

The Prisma schema has 80+ models but the migration history was fragmented
across 5 files with missing tables, columns, unique constraints, and indexes.
Each incremental fix revealed more gaps (AsyncTask missing, country missing,
phone NOT NULL mismatch, ON CONFLICT failures).

Squashed into a single migration generated from the current schema. This:
- Creates all 80+ tables with correct columns, constraints, and indexes
- CI creates a fresh DB each run so no data migration is needed
- Production (Supabase) already has the correct schema from prior deployments"
git push origin main
```

### Production Safety Note

The Supabase production database already has the correct schema (all prior migrations were applied successfully there before they broke in CI). The squashed migration is a **clean-slate** approach for CI only. If the production database ever needs to be rebuilt, the same squashed migration will recreate it correctly.

If production needs an incremental migration (e.g., schema changed since last deploy), run:
```bash
npx prisma migrate diff --from-schema-datasource prisma/schema.prisma --to-schema-datamodel prisma/schema.prisma --script
```
This generates the delta between the current production schema and the desired schema.
