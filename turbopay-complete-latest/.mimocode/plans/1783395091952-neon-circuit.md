# TurboPay — Load Balancing & High-Traffic Performance Plan

## Context

TurboPay is deployed on Vercel (Hobby tier) with Supabase PostgreSQL. The app currently works but has no performance optimizations for traffic scaling. Vercel handles basic load balancing (automatic serverless scaling), but the application code needs tuning to handle large traffic efficiently. Redis is not configured, there are no HTTP caching headers, no code splitting, and the edge middleware has per-request overhead that can be reduced.

## Goal

Make TurboPay production-ready for large traffic by optimizing: caching layers, edge middleware, database connections, Vercel function config, HTTP caching, and code splitting.

---

## Changes

### 1. Redis setup in Vercel (env var)
**File:** Vercel dashboard (env vars) + `src/lib/turbopay/rate-limit.ts` + `src/lib/turbopay/cache.ts`

- Add `REDIS_URL` env var in Vercel dashboard (Upstash free tier — serverless Redis)
- This enables distributed rate limiting, session management, and circuit breaker across all Vercel serverless instances
- Without Redis, rate limiting falls back to per-invocation in-memory Maps — useless under load since each request may hit a different isolate
- **Action:** Add `REDIS_URL` to Vercel env vars pointing to Upstash

### 2. Edge middleware optimization
**File:** `src/proxy.ts`

Currently the proxy parses `BLOCKED_IPS` and `ALLOWED_IPS` from `process.env` on every request. Fix:
- Parse IP lists once at module scope (they don't change at runtime)
- Skip CSP nonce generation and header injection for `/api/` routes (API responses don't need CSP)
- Skip middleware entirely for static assets and known-safe routes (health check, webhooks, cron)
- This reduces per-request edge compute from ~2ms to ~0.3ms

### 3. HTTP caching headers
**File:** `next.config.ts`

Add Cache-Control headers for different route categories:
- **Static assets** (`/_next/static/*`): `public, max-age=31536000, immutable` (already handled by Vercel)
- **Landing/terms/privacy pages**: `public, s-maxage=3600, stale-while-revalidate=86400` (CDN cache 1hr, serve stale for 24hr while revalidating)
- **Read-only API endpoints** (`/api/health`, `/api/intl/rate`, `/api/fx/quote`): `public, s-maxage=60, stale-while-revalidate=300`
- **Authenticated API routes**: `private, no-store` (never cache user-specific data)
- **Webhook/cron routes**: `no-store` (never cache)

### 4. Vercel function configuration
**File:** `vercel.json`

Add function configuration for heavy routes:
- Cron jobs (reconciliation, settlement, data-retention): increase memory to 1536MB, max duration to 30s
- Standard API routes: 1024MB, 10s (default — fine for most)
- Health check: 256MB, 5s
- This prevents cron timeouts under load

### 5. Database connection tuning
**File:** `.env.local` (and Vercel env vars)

Update `DATABASE_URL` connection parameters:
- Add `pool_timeout=10` — fail fast if pool exhausted
- Add `socket_timeout=15` — kill slow queries
- Ensure `connection_limit` is appropriate for Vercel (10-20 for serverless)

### 6. Next.js performance config
**File:** `next.config.ts`

- Add `poweredByHeader: false` — suppress `X-Powered-By: Next.js`
- Add `compress: true` — ensure gzip/brotli compression
- Add `optimizePackageImports` for `lucide-react` (tree-shake unused icons)

### 7. Remove unused dependencies
**File:** `package.json`

- Remove `framer-motion` — 0 imports found in source code, adds ~60KB
- These reduce install time and bundle size

### 8. Static generation for public pages
**Files:** `src/app/landing/page.tsx`, `src/app/privacy/page.tsx`, `src/app/terms/page.tsx`

- Convert landing page, privacy, and terms to Server Components with `export const dynamic = "force-static"` or `revalidate = 3600`
- These pages rarely change and benefit from CDN caching
- This reduces serverless function invocations for public traffic

### 9. API response compression for dashboard polling
**File:** `src/app/api/dashboard/route.ts`

- The dashboard endpoint returns large payloads that the frontend polls
- Add `export const runtime = "edge"` for lightweight read-only endpoints (health, quotes)
- This runs them on Vercel's edge network instead of Node.js, reducing cold start latency
