# TurboPay Critical & High Severity Fix Plan

## Context

Deep architectural audit identified 2 critical and 5 high severity issues in the financial engine. This plan addresses all 7, ordered by blast radius. Each fix preserves existing architecture patterns (double-entry ledger, advisory locks, outbox, hold-confirm-reverse).

---

## Fix 1: Wire `proxy.ts` as Next.js Middleware [CRITICAL]

**Problem:** `proxy.ts` is exported but never imported. No `middleware.ts` exists. All edge-layer defenses (CSRF, session presence, IP blocklist, admin rate limiting, maintenance mode) are inactive.

**File to create:** `src/middleware.ts`

**Approach:** Create `src/middleware.ts` that re-exports `proxy` as the default export (Next.js middleware convention). The `config` with matcher is already exported from `proxy.ts`.

**Edge Runtime blocker:** `proxy.ts` imports `logger` from `@/lib/turbocore/logger`, which uses `node:async_hooks` (AsyncLocalStorage) and `process.stdout.write` — both unavailable in Edge Runtime. The two logger calls (`logger.warn("csrf_rejected", ...)` and `logger.info("admin_request", ...)`) must be replaced with `console.warn`/`console.log` JSON-structured output.

**Changes:**
1. `src/proxy.ts` — Replace `logger.warn(...)` and `logger.info(...)` with `console.warn(JSON.stringify({...}))` and `console.log(JSON.stringify({...}))` respectively. Remove the `import { logger }` line.
2. `src/middleware.ts` — Create with:
   ```ts
   export { proxy as middleware, config } from "./proxy";
   ```
   Wait — Next.js middleware must use `export default` for the handler, not a named export. The correct approach:
   ```ts
   import { proxy } from "./proxy";
   export default proxy;
   export { config } from "./proxy";
   ```
3. Simplify `config.matcher` in `proxy.ts` to just `["/api/:path*"]` (the 19 explicit prefixes are redundant since the first entry is already a catch-all).

**Files modified:** `src/proxy.ts`, `src/middleware.ts` (new)

## Fix 2: Card Transaction Balance Guard [CRITICAL]

**Problem:** `CARD_TRANSACTION_POSTED` webhook handler in `dispatcher.ts:275-300` does unconditional `balanceKobo: { decrement }` with no balance check. Card balance can go negative. The decrement + transaction record create are also not in a Prisma transaction, so a crash between them loses consistency.

**File to modify:** `src/lib/turbocore/webhooks/dispatcher.ts`

**Approach:** Wrap the card debit in a Prisma interactive transaction with a conditional decrement (same pattern as `postDebitLeg` in `ledger.ts`). Also add providerRef dedup check before debiting.

**Changes:**
```ts
case "CARD_TRANSACTION_POSTED": {
  const d = e.data as { providerRef: string; cardId: string; amountMinor: number; currency: string; merchant: string; type: string };
  const card = await db.virtualCard.findFirst({ where: { providerCardId: d.cardId } });
  if (!card) break;

  // Dedup: skip if this providerRef was already processed
  const existing = await db.virtualCardTransaction.findFirst({
    where: { providerRef: d.providerRef },
  });
  if (existing) break;

  // Atomic debit + ledger entry in a single transaction
  await db.$transaction(async (tx) => {
    const updated = await tx.virtualCard.updateMany({
      where: { id: card.id, balanceKobo: { gte: d.amountMinor } },
      data: { balanceKobo: { decrement: d.amountMinor } },
    });
    if (updated.count === 0) {
      // Insufficient card balance — log but don't throw (webhook should still be ack'd)
      return;
    }
    await tx.virtualCardTransaction.create({
      data: {
        cardId: card.id,
        type: "SPEND",
        amountKobo: d.amountMinor,
        currency: d.currency,
        status: "SUCCESS",
        merchant: d.merchant,
        providerRef: d.providerRef,
      },
    });
  });
  break;
}
```

**File modified:** `src/lib/turbocore/webhooks/dispatcher.ts`

## Fix 3: MFA Disable Requires Password Re-authentication [HIGH]

**Problem:** MFA can be disabled with just a session + one TOTP code. A session hijacker can disable MFA and persist access.

**File to modify:** `src/app/api/auth/mfa/route.ts`

**Approach:** When `action === "disable"`, require the user's login password in addition to the TOTP/backup code. This is a standard security pattern — disabling MFA is a high-risk operation that should require re-proving identity.

**Changes:**
1. Extend the disable schema to include `password`:
   ```ts
   const disableSchema = z.object({
     action: z.literal("disable"),
     token: z.string().min(4).max(20),
     password: z.string().min(1, "Enter your password to disable MFA"),
   });
   ```
2. Before verifying the TOTP token, verify the password against the stored hash:
   ```ts
   const dbUser = await db.user.findUnique({
     where: { id: user.id },
     select: { passwordHash: true },
   });
   if (!dbUser?.passwordHash) {
     return errorJson("No password set on this account", 400, "NO_PASSWORD");
   }
   const pwOk = verifyPassword(parsed.data.password, dbUser.passwordHash);
   if (!pwOk) {
     await audit({ userId: user.id, action: "MFA_DISABLE_FAILED", category: "AUTH", severity: "WARN", ip });
     return errorJson("Incorrect password", 401, "INVALID_PASSWORD");
   }
   ```
3. Import `verifyPassword` from `@/lib/turbopay/crypto` (already used elsewhere in the auth module).

**File modified:** `src/app/api/auth/mfa/route.ts`

## Fix 4: Passkey Challenge Store — Redis Fallback [HIGH]

**Problem:** In-memory `Map` challenge store in `passkey.ts` breaks multi-instance deployments. Challenge created on instance A can't be consumed on instance B.

**File to modify:** `src/lib/turbopay/passkey.ts`

**Approach:** Add a Redis-backed challenge store that falls back to the in-memory Map when Redis is unavailable. Use the same lazy Redis connection pattern from `rate-limit.ts` (import `getSharedRedis`).

**Changes:**
1. Import `getSharedRedis` from `@/lib/turbopay/rate-limit`.
2. Create two store implementations:
   - `memStore`: the existing `Map<string, StoredChallenge>` (unchanged)
   - `redisStore`: uses Redis `SET key value EX 300` (5-min TTL) and `GET key` + `DEL key` for consume
3. `storeChallenge()`: try Redis first, fall back to mem.
4. `getAndConsumeChallenge()`: try Redis first (`GET` + `DEL` atomic via Lua or `GETDEL`), fall back to mem.
5. Keep the existing `setInterval` GC for the mem fallback only.

**Files modified:** `src/lib/turbopay/passkey.ts`

## Fix 5: Billing Service — Add Fee Calculation [HIGH]

**Problem:** `billing.service.ts` never calls `fees.calculate()`. Airtime, data, electricity, and utility purchases are processed at cost. Seed data defines fees (0.5% for airtime/data, ₦100/₦50 flat for electricity/utility) but they're never applied.

**File to modify:** `src/lib/turbopay/services/billing.service.ts`

**Approach:** Import the fee engine and calculate fees before calling `debitPipeline`. Pass the fee to the pipeline so the user is debited `amountKobo + feeKobo`. Update side-table rows to record the actual fee.

**Changes for each billing method (buyAirtime, buyData, payElectricity, payUtility):**
```ts
import { fees } from "@/lib/turbocore/fees";

// Before debitPipeline call:
const feeResult = await fees.calculate("turbopay", "<CATEGORY>", amountKobo, { kycTier: user.kycTier });
const feeKobo = feeResult.feeMinor;

// Pass to debitPipeline:
const result = await debitPipeline({
  // ...
  amountKobo: amountKobo + feeKobo,  // total debit includes fee
  // ...
});

// In the side-table create callback:
feeKobo,  // instead of hardcoded 0
```

Where `<CATEGORY>` maps to: `AIRTIME`, `DATA`, `BILL_ELECTRICITY`, `BILL_UTILITY`.

**File modified:** `src/lib/turbopay/services/billing.service.ts`

## Fix 6: Billing Service — Add Idempotency [HIGH]

**Problem:** Bill payments have no idempotency. A retry double-charges the user and double-purchases from the provider.

**File to modify:** `src/lib/turbopay/services/billing.service.ts`

**Approach:** Add idempotency key parameter to each billing method. Use the same `startIdempotency`/`completeIdempotency` pattern from `transfer.service.ts`.

**Changes for each billing method:**
1. Add optional `idemKey?: string` to each method's input interface.
2. At the start of each method:
   ```ts
   if (opts.idemKey) {
     const cached = await getIdempotentResponse(opts.idemKey);
     if (cached.hit) return cached.body;
     const started = await startIdempotency(opts.idemKey, "billing.<method>", user.id);
     if (!started) throw new ServiceError("IDEMPOTENCY_INFLIGHT", "Request already processing", 409);
   }
   ```
3. After successful completion:
   ```ts
   if (opts.idemKey) {
     await completeIdempotency(opts.idemKey, 200, result);
   }
   ```
4. Update the API routes (`/api/airtime`, `/api/data`, `/api/bills/electricity`, `/api/bills/utility`) to read `Idempotency-Key` header and pass it through.

**Files modified:** `src/lib/turbopay/services/billing.service.ts`, `src/app/api/airtime/route.ts`, `src/app/api/data/route.ts`, `src/app/api/bills/electricity/route.ts`, `src/app/api/bills/utility/route.ts`

## Fix 7: Ticket/Dispute Number Race Condition [HIGH]

**Problem:** `generateTicketNumber()` and `generateDisputeNumber()` use count-then-create. Concurrent requests generate the same number, causing unique constraint violations.

**Files to modify:** `src/lib/turbocore/support/index.ts`, `src/lib/turbocore/disputes/index.ts`

**Approach:** Wrap the generate + create in a retry loop. On unique constraint failure, regenerate and retry (max 3 attempts). This is the simplest fix that doesn't require schema changes or DB sequences.

**Changes (identical pattern for both):**
```ts
private async generateTicketNumber(): Promise<string> {
  const year = new Date().getFullYear();
  for (let attempt = 0; attempt < 3; attempt++) {
    const count = await db.supportTicket.count({ where: { createdAt: { gte: new Date(`${year}-01-01`) } } });
    return `TP-${year}-${String(count + 1).padStart(6, "0")}`;
  }
  // Fallback: use random suffix to guarantee uniqueness
  const rand = crypto.randomBytes(3).toString("hex").toUpperCase();
  return `TP-${year}-${rand}`;
}
```

And in `createTicket`:
```ts
for (let attempt = 0; attempt < 3; attempt++) {
  try {
    const ticketNumber = await this.generateTicketNumber();
    const ticket = await db.supportTicket.create({ data: { ticketNumber, ... } });
    return ticket;
  } catch (e: any) {
    if (e.code === "P2002" && attempt < 2) continue; // unique constraint violation, retry
    throw e;
  }
}
```

Same pattern for `createDispute` in `disputes/index.ts`.

**Files modified:** `src/lib/turbocore/support/index.ts`, `src/lib/turbocore/disputes/index.ts`
