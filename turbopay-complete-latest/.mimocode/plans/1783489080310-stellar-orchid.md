# TurboPay Production Improvements Plan

## Overview

Seven production improvements to the existing TurboPay codebase. Each change is scoped to preserve existing functionality while addressing the specific issues outlined in the requirements.

## 1. Persistent Login — Fix Session Persistence Across Browser Restarts

**Root cause identified:** A bug in `src/lib/turbopay/client.ts` line 125 — `tryRefreshToken()` checks for `json?.data?.sessionToken`, but the refresh route (`src/app/api/auth/refresh/route.ts` line 141) returns `{ data: { ok: true } }` (no `sessionToken`). This means `tryRefreshToken()` **always returns false**, causing unnecessary logouts when the access token (24h) expires.

**The cookies themselves are fine:**
- `tp_session`: HttpOnly, path `/`, expires 24h — persists across restarts
- `tp_refresh`: HttpOnly, path `/api/auth/refresh`, expires 30d — persists across restarts

### Changes

| File | Change |
|------|--------|
| `src/lib/turbopay/client.ts` | Fix `tryRefreshToken()` — check `json?.data?.ok === true` instead of `json?.data?.sessionToken`. On success, return `true` so the caller retries the failed request with the new cookie. |
| `src/lib/turbopay/client.ts` | After successful refresh, the new access token is already in the browser cookie (set by server). Just retry the original request — no need to extract tokens from the response. |

### Verification
- Access token expires after 24h → API returns 401 → `tryRefreshToken()` succeeds → request is retried with new cookie → user stays logged in
- Browser restart: both cookies persist → `GET /api/auth/me` on page load returns valid user → dashboard renders

## 4. Performance Optimizations

### 4a. Lazy Load Views in App Shell

**Current state:** All ~30 view components are eagerly imported at the top of `src/components/turbopay/app-shell.tsx` (lines 69-110). This means the entire app's view code is bundled together, slowing initial load.

### Changes

| File | Change |
|------|--------|
| `src/components/turbopay/app-shell.tsx` | Replace eager imports (lines 69-110) with `React.lazy()` + dynamic imports for every view component. Wrap `renderView()` in `<Suspense>` with a lightweight fallback. Admin views are especially good candidates since most users never see them. |
| `src/components/turbopay/app-shell.tsx` | Add `React.memo()` to `NavButton` component to prevent unnecessary re-renders on sidebar state changes. |

### 4b. Optimize React Rendering

| File | Change |
|------|--------|
| `src/components/turbopay/app-shell.tsx` | Memoize `renderView()` result or move view selection to a separate component to avoid re-rendering the entire shell on sidebar/notification state changes. |
| `src/components/turbopay/app-shell.tsx` | Memoize `renderNavGroups()` with `useCallback` to prevent nav re-renders on unrelated state changes. |

### 4c. Optimize useApi Hook

| File | Change |
|------|--------|
| `src/lib/turbopay/client.ts` | Add `stale-while-revalidate` semantics to `useApi` — serve cached data immediately while revalidating in the background (currently it shows loading state on every re-render). |

### 4d. Bundle Size

| File | Change |
|------|--------|
| `next.config.ts` | Add `optimizePackageImports` for heavy packages: `recharts`, `date-fns`, `@radix-ui/*` (some are already optimized for lucide-react). |

## 5. Fix "No Active Virtual Account" Bug

**Root cause:** `WalletService.fund()` in `src/lib/turbopay/services/wallet.service.ts` line 77-78 queries for an ACTIVE virtual account and throws if none exists. But the wallet view route (`GET /api/wallet`) returns `virtualAccount: null` without error — meaning users see their wallet but get an error when trying to fund.

The fix: When funding and no active virtual account exists, **auto-create one** using the existing `ensureWallet()` function (which is already idempotent and handles both mock and real provider creation).

### Changes

| File | Change |
|------|--------|
| `src/lib/turbopay/services/wallet.service.ts` | In `fund()` method (line 77): instead of throwing `VIRTUAL_ACCOUNT_NOT_FOUND`, call `ensureWallet(user.id, user.fullName)` to auto-create a virtual account, then proceed with funding. Only throw if `ensureWallet` also fails. |
| `src/app/api/wallet/route.ts` | In `GET /api/wallet`: if no ACTIVE virtual account found, call `ensureWallet()` to provision one on first access (idempotent — safe to call repeatedly). |

## 6. Improve Error Handling

Replace generic error messages with contextual, actionable messages. Implement graceful retries where appropriate.

### Changes

| File | Change |
|------|--------|
| `src/lib/turbopay/services/wallet.service.ts` | Replace "No active virtual account" with auto-creation (covered in item 5 above). If creation fails, return contextual error: "Virtual account setup is in progress. Please try again in a few moments." |
| `src/lib/turbopay/funding.ts` | For `ACCOUNT_NOT_FOUND` (line 29): return more specific reason like "NO_VIRTUAL_ACCOUNT" |
| `src/lib/turbopay/errors.ts` | Add `VirtualAccountError` class with contextual codes: `PROVISIONING`, `PROVIDER_UNAVAILABLE`, `NOT_FOUND` |
| `src/app/api/wallet/fund/route.ts` | Handle the new error types with appropriate HTTP status codes and user-facing messages |
| `src/lib/turbopay/client.ts` | In the global error handler: show more specific toast messages based on error code (e.g., "Provider temporarily unavailable" vs "Account setup in progress") |

### Error message mapping

| Old message | New message |
|-------------|-------------|
| "No active virtual account" | Auto-creates account; if that fails: "Setting up your virtual account. Please try again shortly." |
| "Wallet not found" | "Your wallet is being set up. This usually takes a few seconds." |
| "Funding failed" (generic) | Show specific reason: provider unavailable, amount limits, etc. |
