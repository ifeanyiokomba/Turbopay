# TurboPay Financial Operating System — Implementation Plan

## Context

The stripe.txt document defines a 13-phase architecture to evolve TurboPay from a payment app into a Financial Operating System. The codebase already has a strong foundation: provider interfaces, plugin framework, adapter factory, registry, routing engine, health monitoring, circuit breaker, and 10+ provider adapters. The work is to extend, not rewrite.

### Phase 4: Capability-Aware Routing

**Goal**: Route transactions by capability, not just provider name.

**Files to modify:**
- `src/lib/turbocore/config/routing-engine.ts` — Add capability filter before scoring:
  1. Query `PluginRegistry.findByCapability(requiredCapability)`
  2. Filter candidates to only those with the capability
  3. Then apply existing scoring (health, latency, success rate, cost)

**New routing flow:**
```
Transaction Request
  → Extract required capability (e.g., "bill_payment:pay")
  → PluginRegistry.findByCapability(capability) → [flutterwave, remita, quickteller]
  → Filter by health, circuit breaker
  → Score by latency, success rate, cost, country/currency
  → Select best provider
  → Execute
```

## Implementation Order

1. **Phase 1** (Capability Engine) — Foundation for everything else
2. **Phase 2** (Flutterwave Adapter) — Largest new provider
3. **Phase 3** (Onafriq Adapter) — PAPSS + mobile money
4. **Phase 4** (Capability-Aware Routing) — Uses capabilities from Phase 1
5. **Phase 6** (Plugin Adoption) — Convert adapters to plugins
6. **Phase 5** (Dynamic Service Registry) — Frontend driven by capabilities
7. **Phase 7** (Admin Enhancements) — UI improvements
8. **Phase 8** (Webhook Handlers) — Standardize webhook flow

## Key Principles (from stripe.txt)

1. **Never rebuild** — refactor, extend, improve. Backward compatibility is required.
2. **Provider abstraction is non-negotiable** — all external deps as interfaces.
3. **No provider branding** — users see "Payments", "Bills", etc., not "Paystack" or "Flutterwave".
4. **Capabilities over assumptions** — query what providers CAN do, don't guess.
5. **Intelligent routing** — best provider for each specific capability.
6. **Failover** — if one provider fails, try the next. User never notices.
